# Plan: the starter catches up with gastos and blueprint2

Written 2026-10-12 from a review of `../gastos` (Go, at `bde7b6e`),
`../blueprint2` (Go, on this starter, at `3142e35`) and `../pv4`
(rustrillo, Rust, at `49aef8b`) against this starter at `fee5f01`.
Revised the same night after two corrections from the owner: pv4's
build loop is now `cargo check` under 1 s, a test build in 3 to 5 s,
the app's tests in 3.8 s and a lane worktree under 1 GB real disk
(pv4's `docs/build-performance.md`, not yet on master); and Blueprint
is already ported, in `../blueprint2`, 74 commits in two days.

## What the review found

**The Rust arm's kill criterion is open, not failed.** The gap to Go
is now roughly 3 to 10x on the inner loop, and what remains is CPU
under a fleet and the trybuild step. The decision is made by numbers
on the same drills (gastos ADR 0001, pv4 ADR 0001's step 6), and the
Go side of those numbers is being produced right now in blueprint2.
Record them while they are fresh. Nothing in this plan touches pv4.

**Tenancy is decided in Go, in blueprint2, and differently from pv4.**
Blueprint2's ADR 0005 and 0006: one process per tenant as a systemd
template unit, socket-activated, exiting when idle
(`libs/activation`); identity central in `apps/admin`
(`libs/signin`); tenants hold no credentials. Measured 55 ms cold and
about 50 MB idle. "One process serving many SQLite files" was
rejected there. The deployment economy the Rust arm was chosen for is
mostly reclaimed by that shape: an idle tenant has exited, so only
concurrently active tenants pay 50 MB each. A single binary is not
built; pv4's resolver seam (ADR 0002 there) stays the documented
option, triggered by a measurement of active-tenant memory, with the
note that pv4 showed a front router resolving the whole app per
tenant leaves handlers untouched, so blueprint2's "every handler
would change" is not the cost. The cost is per-tenant uid isolation,
memory caps and Litestream per unit.

**Postgres is a Teselly-time decision.** Blueprint2's
`docs/tenant-storage-investigation.md` leans SQLite for Blueprint-sized
tenants and Postgres, one database per tenant from day one, for
Teselly. No rastrillo fork was needed by either Go repo (blueprint2
ADR 0006: "no upstream change needed"). A fork is for Postgres only,
limited to the data layer (`db`, `migrate`, `dbtest`, `secondfactor`),
wired by a `replace`, SQLite path byte-identical. pv4's Postgres guard
(permanent triggers derived from the declaration at boot, intent via
`set_config`, append-only including TRUNCATE, ids from a counter
table) is the design to translate then.

**The exposure is drift between the three Go repos.** The starter is
behind both, and they are behind each other:

| Grew in | What | In starter | In the other |
|---|---|---|---|
| blueprint2 | `libs/changes`: scope (`Within`, `WithinCreated`, `InScope`), `on_behalf_of`, `Policy.Admit`, `Policy.Committed`, `Trail.OnRecord`, `ErrBadScope`/`ErrScopeConflict`/`ErrScopePending`/`ErrNotAdmitted`, migrations 0003 and 0004 | no | gastos: no |
| blueprint2 | `libs/activation` (socket activation, idle exit) | no | gastos: no |
| blueprint2 | the doorbell (`kit/bell.go`, `Committed: bell.Ring`, `static/live.js`), ADR 0004 as built | no | gastos: no |
| blueprint2 | feature packages with `kit`, `clients/` as a module kind, `signintest` as the Given | no | gastos: no |
| blueprint2 | rulings: a change is a state change that matters to the business, transient work is plumbing; a cause is a parent only within one request | no | gastos: no |
| gastos | per-reason allow-list (`Policy.Allow`, `ReasonWrites`, `writes_test.go`) | no, "held in reserve" | blueprint2: no |
| gastos | route coverage gate (`coverage_test.go`) | no | blueprint2: no, with 45 scenario files |
| gastos | `/changes.json` feed, the oracle | no | blueprint2: no |

A new app cut from the starter today misses both columns, and
blueprint2 is missing gastos's two gates.

### Unit 1: the starter takes blueprint2's libs and rulings

Blueprint2 is the source; this is mechanical.

- `libs/changes` and `libs/telemetry` become blueprint2's, by diff.
  `apps/myapp` exercises scope (`Within` on one entry point) and
  `on_behalf_of` is shown on `/changes` when set.
- `libs/activation` copied as is, wired in `apps/myapp`'s `main.go`
  behind `MYAPP_IDLE_TIMEOUT`.
- The doorbell's generic half: `Bell` and the stream loop split from
  `Kit.Stream` (the attach lines stay in blueprint2) into
  `libs/doorbell`, with `live.js` as a shared static asset. ADR 0004
  moves from proposed to accepted as built, with blueprint2's
  amendments.
- `AGENTS.md`: the two rulings above, the feature-package layout
  (`internal/<app>/kit`, `<feature>/Mount(r, Deps)`), `clients/` as a
  module kind, and "Given signs in" as an alternative to "Given joins
  through `/signup`" where a product has central identity. Vanilla
  sign-up on the instance stays the starter's default.
- ADR 0005 here: tenancy for apps on this starter is blueprint2's
  shape (process per tenant, socket activation, idle exit), with the
  single-binary resolver as the measured option.

Done is verified by: `make ci` green; `diff -r libs ../blueprint2/libs`
empty for `changes`, `telemetry`, `activation`; a scenario in myapp
that rings a listener on a commit and nothing on a rollback.

Size: a day and a half.

### Unit 2: the gastos gates, into the starter and into blueprint2

- `libs/changes`: `Policy.Allow map[string]Writes`,
  `ErrReasonMismatch`, `fits()` in `require` (nil turns it off); the
  refusal test.
- Each app: `<context>Writes` in its `reasons_<context>.go`,
  `ReasonWrites`, `Allow:` in `changes.Install`, `writes_test.go`.
- `coverage_test.go`: every mounted route reached by a scenario or a
  named exception; stale exceptions fail.
- `GET /changes.json?after=<id>` with the field contract; the harness
  logger wrapped in `telemetry.Correlate`.
- Optional: `apps/<app>/oracle/` (build tag `oracle`, a test package,
  not a program) with `make oracle`.
- Land in the starter first, then in blueprint2 as one PR per app
  (`server`, `admin`). Blueprint2's route gate will surface routes no
  scenario reaches; each gets a scenario or a reason.
- `AGENTS.md`: the allow-list leaves "held in reserve".

Done is verified by: a planted write on an undeclared column refused
with `ErrReasonMismatch`; a planted unreached route fails
`coverage_test.go` by name; `make ci` green in both repos.

Size: a day in the starter, one to two days in blueprint2 depending
on how many routes the gate surfaces.

### Unit 3: censuses, as tests

- `changes.Install` refuses at boot a table that is neither tracked,
  untracked with a reason, nor plumbing, naming it (pv4 RUS-25; the
  starter has it only as a test).
- An escape-hatch census: `SkipHooks`, raw `Exec`/`Raw` on a tracked
  table, `sql.Open` outside `cmd/`, each a named exception with a
  reason (pv4 seams ADR, rule 3).
- The `ci` line: every target it names runs, or the gate says which it
  skipped and why. Blueprint2's `island-check` and `steward-check`
  already print a loud SKIP; make that the pattern.

Size: a day. Beside unit 2.

### Unit 4: Postgres, when Teselly asks (ADR 0006 here)

Not started before. The fork at rastrillo `v0.28.0` via `replace`,
the data layer only; pv4's Postgres guard into `libs/changes`;
migration sets per backend with a test that the two directories carry
the same names; `make pg-up` and `ci-pg` from pv4; SKIP without the
URL, named. Done is verified by the scenarios green on both backends,
`verify` clean on both, one scenario's change records identical on
both except timestamps (pv4 reached this).

Size: a week.
